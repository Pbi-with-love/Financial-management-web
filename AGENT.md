# AGENT.md

Instructions for AI coding agents working on this repository. Read this file fully before writing or changing code.

## Project in one sentence

An internal web app for a small group that keeps a shared fund: members deposit money, shared expenses (e.g. grocery runs) are entered item by item, each item is split among the members who used it, and every member can see their balance and exactly what they paid for, when.

## Core principle: the ledger is the source of truth

- **Never store balances.** A member's balance is always computed:
  `balance = sum(deposits) − sum(item_shares)`, excluding voided records.
- **Never hard-delete financial records.** Deposits and expenses are corrected by setting `voided = true` and, if needed, entering a new record. History must stay intact.
- If you are about to add a `balance` column, a cached total, or a `DELETE` on a financial table, stop. It violates this principle.

## Domain rules (must always hold)

### Money

- **All amounts are integers in cents** (`3000` = €30.00), in the database, in the API, and in all calculations.
- Never use floating-point arithmetic on money. Convert to a display string (`€30.00`) only in the frontend.
- Amounts in requests must be positive integers. Reject `0`, negatives, decimals, and strings.

### Expenses and items

- An **expense** is one shopping trip or payment (title, date, optional note).
- An expense has **one or more items** (description, amount, category).
- `expense.total` must equal the sum of its items. The server computes it; never trust a total sent by the client.
- Each item has a list of **participants** (member IDs). Default: all active members.

### Splitting

- The server, not the client, computes every `item_share`.
- Even split uses `splitEvenly(totalCents, memberIds)`:
  - `base = floor(total / n)`, `remainder = total % n`
  - the first `remainder` members (sorted by member ID for determinism) get `base + 1`
  - **invariant:** the shares of an item always sum exactly to the item amount
- Custom split (optional per item): the client sends explicit cent amounts per member; the server rejects the request unless they sum exactly to the item amount.
- Creating an expense with its items and shares happens in **one database transaction**. Either everything is written or nothing is.

### Voiding

- `POST /expenses/:id/void` and `POST /deposits/:id/void` set `voided = true` and `voided_at`.
- Voided records are excluded from balances and reports but still appear in history, marked as voided.
- Voiding twice is a no-op that returns the same result (idempotent), not an error.
- Editing an expense = void the old one + create a new one. There is no in-place update of amounts.

### Members

- Members are deactivated (`active = false`), never deleted, because history references them.
- Inactive members are not offered as default participants but keep their balance and history.
- A negative balance is allowed (someone owes the fund), but the UI must show it clearly in red.

## API conventions

- JSON in, JSON out. All money fields end in `Cents` (e.g. `amountCents`, `balanceCents`).
- Dates are ISO 8601 strings (`2026-10-28`). Store expense dates as `date`, timestamps as `timestamptz`.
- Validation error → `400 { "error": "message" }`. Not found → `404`. Unexpected → `500` with a generic message (log the details server-side, never leak stack traces).
- Controllers pass errors to `next(err)`; only the error middleware formats error responses.

## Testing requirements

Every change to `domain/` or `services/` needs tests. These cases must always be covered:

- `splitEvenly(4000, [A, B, C])` → `1334, 1333, 1333`, sum = 4000
- `splitEvenly(3000, [A, B, C])` → `1000` each
- One participant → full amount to that member
- Custom split that does not sum to the item amount → rejected
- Expense with two items and different participants (e.g. shared food + beer for two people) → correct per-member totals
- Voided expense → excluded from balance; voiding twice → no error, no double effect
- Balance = deposits − shares, checked against the worked example in README.md
- Creating an expense where one item fails validation → nothing is written (transaction rollback)

## Things you must not do

- Do not store or cache balances.
- Do not use `Number` division on money without the remainder handling in `splitEvenly`.
- Do not hard-delete members, deposits, expenses, items, or shares.
- Do not compute shares or totals in the frontend and send them as truth.
- Do not commit `.env` files or secrets. Only `.env.example` with placeholders.
- Do not edit generated Prisma migrations by hand.
- Do not add authentication libraries or user accounts unless asked; v1 uses a single shared password (see README).

## When requirements are unclear

Prefer the simplest behavior that keeps the ledger correct and auditable, write down the assumption in the commit message, and add a test that pins it down.
